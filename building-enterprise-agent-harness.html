Part 01The Core Concepts That Govern Agent Harnesses

The quiet shift: from weights to context to harness

The history of LLM systems is a story of progressive outward movement. Capability began in model weights, moved into prompts and retrieval, and now increasingly lives in the infrastructure around the model.

Memory stores, reusable skills, standardized protocols, sandboxes, approval gates and observability pipelines together form the agent harness. The driving logic is externalization. Long-term continuity, stable multi-step execution and governed interaction with external systems are hard for a language model to carry internally, so the harness moves those burdens into explicit, inspectable and reusable structures.

Recall becomes retrieval. Improvised generation becomes guided composition. Ad hoc coordination becomes a machine-readable contract.

The practical consequence is profound: the same foundation model can behave like two different systems depending on the harness around it. Research on production coding agents suggests that changing the harness without changing the model can alter task success by as much as 2×. When reliability matters, harness engineering is the architecture.

Dimension 01Memory: externalized state across time

A bare model is stateless. Every call begins from a fresh context, so continuity must be reconstructed rather than carried forward. Mature systems externalize at least four kinds of state:

  • Working state: open files, partial plans and execution checkpoints for the current task.
  • Episodic state: prior decisions, tool calls, failures, outcomes and reflections.
  • Semantic state: domain facts, heuristics and project conventions that outlive one episode.
  • Personal or environmental state: stable preferences, habits and recurring constraints.

Memory architecture has moved from monolithic context to retrieval stores, hierarchical memory with extraction and forgetting policies, and adaptive systems that learn retrieval and routing. The hard problem is not storage but control: making the right history legible at the right moment so limited model attention is spent on reasoning rather than remembering.

Dimension 02Skills: externalized procedural expertise

A skill is not a tool. A tool exposes an action; a skill encodes when and how to use actions to complete a meaningful class of tasks. Skills externalize operating procedures, decision heuristics and normative constraints into artifacts that can be discovered, loaded, versioned and composed.

SpecificationDeclare boundaries, preconditions and constraints.
DiscoveryMatch the right procedure to the current task.
Progressive disclosureLoad summaries first and full detail only when needed.
Execution bindingConnect procedures to tools, files and sub-agents at runtime.

Every execution becomes the selection and following of a pre-validated operating path rather than a fresh improvisation—which is exactly what enterprise reliability requires.

Dimension 03Protocols: externalized interaction structure

Interactions with tools, agents and users should not be left to free-form prompting. Protocols move invocation grammar, argument schemas, lifecycle semantics, permission boundaries and discovery metadata into machine-readable form.

  • Interoperability: tools and agents compose across vendors.
  • Governability: permissions and audit attach to structured interfaces.
  • Portability: models and runtime components can change without rewiring everything.

The unifying layerThe harness as a cognitive environment

Memory, skills and protocols are the raw materials of externalized cognition. The harness makes them cohere through six recurring design dimensions:

Control flowPerceive, retrieve, plan, act and observe—with explicit limits.
SandboxingBound reads, writes and execution; make failures recoverable.
Human oversightApproval gates and escalation triggered by actual risk.
ObservabilityStructured traces and metrics for debugging and audit.
PolicyLayered user, project and organization rules enforced at runtime.
Context budgetsAllocate finite attention across history, memory, skills and tools.

None is intelligence by itself. Together they form the environment that determines what an agent can know, remember and do.

Part 02Four Architectural Philosophies

Production harnesses cluster around four bets: engineering depth inside one box, hard safety rails, extensible minimalism, or batteries-included completeness.

OpenCode — engineering depth

TypeScript / Bun · MIT · approximately 157k stars. OpenCode concentrates mature engineering in one terminal-first harness: overflow-aware compaction, output reservation, tree-sitter command analysis, five-tier configuration merging, typed tools and plugin hooks. Provider breadth is narrower, human pause/resume is coarse, and day-two operations stop at logs plus optional telemetry. It fits teams that want to inherit a deeply engineered single-box implementation.

Claw-Code — hard safety rails

Rust · license unspecified · approximately 191k stars. Claw-Code makes safety structural. Linux namespaces isolate user, mount, IPC, PID, UTS and network access; hard iteration caps and panic-catching terminate runaway loops; lazy tool loading and sub-agent allowlists enforce least privilege. License ambiguity, partial hardening, missing cost telemetry and a steeper Rust talent requirement are material adoption constraints.

Pi — minimal core, maximum extensibility

TypeScript / Bun · MIT · approximately 47k stars. Pi keeps the loop small and makes advanced behavior composable. It supports more than thirty-five providers, twenty-plus lifecycle hooks, tree-structured sessions and pluggable SSH, Docker or managed execution backends. Multi-agent behavior, MCP, plan mode, language-server integration and loop safety must be sourced or built; skills are stronger at discovery than execution.

DeepAgents — batteries included

Python / LangGraph · MIT · approximately 22k stars. DeepAgents ships graph orchestration, native freeze/resume, memory, sub-agents, progressive skill disclosure, model profiles, tracing, evaluation, IDE integration and remote sandboxes as first-class features. Permissions outside the filesystem remain less granular, shell safety is backend-dependent, failure-count circuit breaking needs an additional layer, and adopters inherit framework churn.

What the comparison teaches

  • Depth over breadth: choose the engineering-depth approach when you want to inherit a mature terminal-first system.
  • Safety by construction: choose the safety-first approach when hard isolation outweighs license and staffing constraints.
  • Extensibility over completeness: choose the minimal core when the harness itself is a platform your organization wants to own.
  • Completeness over minimalism: choose batteries-included when oversight, observability, evaluation and provider choice must work from day one.

Most enterprises will converge on a hybrid: the safety-first approach’s loop discipline, the batteries-included approach’s skill disclosure, and the extensible approach’s provider abstraction.

Part 03What an Enterprise Agent Harness Looks Like

A developer agent has one user, one machine and one risk appetite. An enterprise platform has thousands of users, shared data, many workloads, compliance obligations and a hard requirement that every action be explainable afterward.

In that environment, the harness is the operating system that makes model-based reasoning usable, controllable, repeatable and accountable. Explore the production blueprint and its two-speed operating model below.

01

Identity is the boundary

Every run establishes organization, user, conversation, agent configuration, model, data, tools, permissions and approval rules. Two users may ask the same question and correctly receive different answers.

02

State is explicit, not prose

Messages, files, citations, tasks, tool results, approvals, artifacts and delegation status live in structured fields, making runs validatable and resumable.

03

Externalization organizes the system

The model keeps interpretation, synthesis and adaptation. Mutable, reusable, inspectable and enforceable state lives outside it.

04

The loops are two-speed

A fast operational loop executes work inside a slower governed loop that tests, reviews, releases and rolls back improvements.

Production blueprintThe layers of an enterprise harness

Identity and operating context

  • Carry authenticated user and organization context on every run.
  • Assign agent capabilities explicitly; never make them globally available.
  • Apply the same isolation boundary to data, memory, files, caches, tools and logs.

Memory as managed continuity

  • Separate working, episodic, organizational and personal memory by owner, lifespan and policy.
  • Retrieve selectively with provenance instead of loading the whole archive.
  • Define retention, correction, deletion and conflict-resolution rules.
  • Record who created each memory, what supports it, who may retrieve it, when it expires, and whether it was stated or inferred.

Skills as governed operational knowledge

  • Make procedures discoverable, versioned and explicit about tool and file dependencies.
  • Keep only a small catalog in context; load full instructions when a task matches.
  • Require validation and regression evidence before publication, with rollback available.
  • Let traces propose improvements, but never publish a procedure without review.

Filesystem as external working memory

  • Use a bounded task workspace; path resolution fails closed.
  • Separate inputs and outputs, prevent accidental overwrite, and search large collections before loading them.
  • Persist artifacts with provenance, conversion history and sensitivity labels.
  • Treat stored content as data, never as instructions: path safety does not imply content trust.

Tools, delegation and protocols

  • Validate machine-readable tool inputs and return structured outputs with platform-managed authentication.
  • Make side effects idempotent or status-checkable so timeouts do not duplicate actions.
  • Bound delegated context, depth, time, budget and capability; children do not inherit everything by default.
  • Use standard tool, agent-to-agent and user-interaction protocols to preserve portability.

Orchestration and control

  • Use an explicit loop with ordered middleware: policy before execution, registration after.
  • Set separate limits for model calls, tools, elapsed time, context, spend and delegation depth.
  • Distinguish success, refusal, cancellation, timeout, denial and pending approval.
  • Checkpoint before pauses and multi-step work so resuming never repeats a completed side effect.

Policy and human oversight

  • Make one central decision before every action: allow, deny, require approval, or allow with enhanced audit.
  • Use short-lived, narrowly scoped credentials and read-only access where possible.
  • Reserve approvals for consequential, hard-to-reverse actions so users do not learn to click through.
  • Carry data controls through memory, prompts, tools, sandboxes, files and external systems.

Observability and evaluation

  • Reconstruct every run from model and configuration versions, tokens, tool outcomes, approvals, sources, cost, errors and trace identifiers.
  • Evaluate both the answer and the harness: retrieval precision, context efficiency, recovery, policy coverage, skill compatibility and cost under load.
  • Route proposed changes through tests, review, staged release, monitoring and rollback.

Closing perspectiveBuild the environment, not only the reasoner

The capabilities cannot be designed in isolation. Memory affects context. Skills determine tool use. Tools create artifacts and side effects. Policy governs those actions. Observability records them. Evaluation turns the records into evidence for improvement.

An enterprise harness turns a general-purpose model into a governed participant in real work. Remembering becomes retrieving; handling documents becomes working in a bounded workspace; knowing a process becomes loading a procedure; calling a system becomes filling a validated interface; taking a consequential action becomes a policy decision; pausing becomes a recoverable checkpoint; and debugging becomes inspection of evidence.

Stop asking “which model should we use?” first. Ask: “what environment have we built for the model to operate in?”

Better agents are not merely better reasoners. They are better organized cognitive systems.
