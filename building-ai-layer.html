Most public discussion of AI architecture assumes a blank canvas: a new product, a new data model, and a team free to pick the best tool for every layer without history to account for. That is useful, but it describes a minority of the AI projects happening inside established companies.

The more common situation is an organization with a mature platform, years of data, existing users, integrations and operational habits that now needs to add AI capability without breaking any of them.

Building AI on top of a legacy platform is not a smaller version of building AI-native. It is a different problem with a different success criterion.

AI-native teams optimize for the best possible architecture for AI workloads. Legacy-plus-AI teams optimize for the best architecture that can be added without a multi-year rewrite, without disrupting an existing user base, and without asking every team that owns a piece of the legacy stack to change how they work. That constraint shapes almost every decision below.

The eleven decisions run from where data comes from, to how models are hosted, to how the whole system is tested and deployed. Technology names are illustrative: they are real open-source and commercial building blocks commonly found in this kind of stack, not a description of any single company’s implementation.

Decision 01Raw Data

In a legacy environment, raw data almost never starts clean. It has accumulated across relational databases, batch-loaded warehouses, flat-file drops and departmental spreadsheets that never reached a central system. Treating all of this as a data-quality problem that must be fixed before AI can begin usually stalls the work for months.

A more workable approach treats the raw layer as a fixed constraint rather than a renovation target. A thin ingestion layer sits beside the legacy stores. Change-data-capture tools such as Debezium stream row-level changes without touching source schemas, then land the stream in an object store or a lakehouse format such as Delta Lake or Apache Iceberg. The result is versioned, queryable raw data without forcing a rigid schema on day one.

  • Choose how much history to backfill and how much to stream incrementally.
  • Run transformations in a shared layer such as Spark or dbt rather than inside every source.
  • Resolve conflicts between overlapping legacy sources automatically, not by manual reconciliation.

Decision 02Clean Data

The clean version of the data rarely lives in one warehouse. It is more often a combination of a fast columnar store for aggregates, such as ClickHouse; DuckDB for embedded analytical queries; a search index such as OpenSearch or Elasticsearch for unstructured and semi-structured content; and curated lake tables for anything that must be queried at scale or replayed.

The consequential choice is whether the AI layer talks directly to those stores or through a semantic layer. Direct access is quicker to build, but it couples every agent and tool to the internal shape of legacy systems. A semantic layer—implemented as a metrics layer such as dbt Semantic Layer or Cube, or as a thin internal API—takes longer to establish but isolates downstream systems from later storage changes.

The pragmatic middle ground is a clean interface defined by business concepts—a customer, an order, a plan, a document—rather than table names, with adapters underneath that map those concepts to the storage technology already in place.

Decision 03Model Hosting

Legacy platforms rarely host their own foundation models, and there is little reason to start. A more durable pattern treats model access as interchangeable endpoints hosted by cloud infrastructure providers such as Azure OpenAI, AWS Bedrock and Google Vertex AI, or directly by model providers such as OpenAI and Anthropic.

Those endpoints sit behind a thin routing and caching layer rather than being called from application code. This matters because many independent teams and applications will eventually need models. Without a shared gateway, each codebase grows its own provider choice, retry logic, caching and cost accounting.

An AI gateway such as LiteLLM or Portkey can centralize routing, provider fallback, response caching and per-tenant usage accounting. It becomes the place to change models later without touching every downstream consumer.

Decision 04Agent Harness

The agent harness is the orchestration brain. It decides what an agent does step by step, what it remembers, which tools it can reach, and how it talks to the rest of the platform. On a legacy platform, this harness is best built as a genuinely new service rather than attached to application logic designed for deterministic, human-triggered workflows.

  • A graph-based engine such as LangGraph makes reasoning and tool calls an explicit state machine rather than one long prompt.
  • Context compaction and response caching keep long conversations within model context limits.
  • Tiered memory can split fast session state in Redis from longer-lived user, organization and project memory.
  • Reusable, instruction-based capabilities let agents invoke common behavior consistently.
  • A locked-down container or microVM such as gVisor or Firecracker isolates code execution.
  • Open protocols such as MCP standardize access to third-party systems instead of creating one-off integrations.

The legacy-specific difficulty is integration surface area. The harness needs adapters for the authentication, data access and business-logic APIs the existing platform already exposes, which is usually the largest and messiest part of the work.

Decision 05Database Supporting the Agent Harness

Reusing the legacy databases for agent state, conversations, tool-call logs, configuration and memory is tempting, but agent workloads have different access patterns: high write volume, short-lived records and graph-like relationships between memory and context. Mixing them with core transactional or analytical workloads creates operational risk for both.

A cleaner pattern is a small purpose-built set of stores: PostgreSQL for structured configuration and ingestion metadata, a document store such as MongoDB for conversation history and logs, and a graph database such as Neo4j or FalkorDB for relationships among systems, agents and tools. Separation lets the AI layer evolve, scale and fail independently without threatening systems of record.

Decision 06Serving Apps

The serving layer exposes the AI capability to people and other systems. A lightweight asynchronous framework such as FastAPI handles the long-lived streaming connections used by agent responses better than a traditional synchronous web framework.

The key decision is whether the AI layer gets its own front door or is folded into the legacy application’s serving layer. A separate, versioned API using server-sent events or WebSockets can be deployed independently, then embedded into existing user interfaces through lightweight integration rather than a full front-end rewrite. The AI layer can ship on its own cadence without forcing a synchronized release train.

Decision 07Auth Layer

Identity is one area where reuse is usually correct. A second identity system creates dual login experiences and a second source of truth for access. The stronger pattern is federation: keep the legacy identity provider authoritative, use OAuth 2.0 or OpenID Connect for delegated authorization, then map existing tenant and user roles into role-based access control for the AI layer.

Agents add a second dimension. The authorization model must reason about both who is asking and what the agent may touch on that person’s behalf. Legacy role systems were rarely designed for delegated agent authority, so this is usually an extension rather than a direct reuse.

Decision 08Monitoring Layer

AI observability must answer questions legacy monitoring was not built to ask: what did an agent decide, why, which tools did it use, and what did the run cost? Dedicated LLM tracing—through Langfuse or an OpenTelemetry-based pipeline—belongs alongside existing infrastructure and application monitoring.

  • Trace-level visibility into agent steps and tool calls.
  • Usage and cost accounting per user and tenant.
  • Infrastructure metrics and dashboards through Prometheus, Grafana and OpenTelemetry.

Emitting through a standard such as OpenTelemetry lets the AI layer’s operational data flow into the monitoring stack the existing operations team already trusts.

Decision 09Security Layer

The AI layer has to cover both traditional application security and agent-specific risks: prompt injection, unsafe tool invocation and code executed inside a sandbox. The model gateway is the natural enforcement point for input and output filtering, guardrails and provider-level safety controls.

System instructions should constrain agent behavior; automated static analysis such as Semgrep or Snyk should inspect generated or executed code; and hardened, minimal base images should limit the sandbox. This does not replace the legacy platform’s security posture. It extends it to an attack surface that did not exist before agents were introduced.

Decision 10Testing Layer

Traditional CI/CD validates deterministic code: the same input should produce the same output. Agents can produce different but equally valid responses, so conventional assertion-based testing is insufficient.

Two tracks need to run together. Standard unit, integration and end-to-end tests cover deterministic components. An evaluation framework uses model-based or rubric-based scoring against a curated scenario set to evaluate agent and tool behavior continuously. Existing pipelines in Azure DevOps, Jenkins or GitHub Actions can usually be extended rather than replaced.

The evaluation harness should live beside tracing. That way a regression caught by an automated evaluation and one reported by a user can be debugged from the same run data.

Decision 11Deployment

Agent runtimes, tool workloads, sandboxes and connector servers have different resource and scaling profiles. Deploying them inside the legacy application creates noisy-neighbor risk: a runaway sandbox process should never degrade the core service.

Separate Kubernetes namespaces or node pools can isolate the agent and tool layer, standardized connector servers, and sandboxed or heavy compute execution. Each can be deployed independently from the legacy platform’s release pipeline. This is what makes “a layer on top” real in production: the AI layer can be scaled, redeployed or rolled back without touching the system underneath it.

Five coherent viewsHow the Pieces Fit Together

A list of good individual choices is not yet a coherent system. The architecture must hold up when viewed through structure, workflow, call order, data movement and state.

Static architectureWhat exists and where the boundaries sit.
WorkflowWhat order a request follows from intake to completion.
SequenceWhich component calls which, and what stays asynchronous.
Data flowWhere knowledge and configuration originate, move and land.
LifecycleWhat state a turn occupies, including interruption and recovery.

Workflow view

A prompt moves through three phases. Intake authenticates against the legacy identity provider and resolves tenant context. Context and execution load conversation and retrieval state, then alternate between model reasoning and tool calls across internal systems, external connectors or a sandbox. Completion streams the response while a background job persists the turn and summarizes it for the next compact context window.

Sequence view

The API loads thread and tenant configuration before handing off to orchestration. The engine and model exchange messages in a loop: the model asks for a tool, the engine executes it with scoped context, and the structured result becomes the next model input. The final response streams immediately; message persistence and queued summarization happen after the user already has the answer, keeping bookkeeping off the critical path.

Data flow view

Knowledge and configuration move through parallel asynchronous paths. Documents become ingestion jobs, then chunks and embeddings in a vector-capable store. Tenant configuration becomes normalized entities in a graph store. Retrieval joins semantic and graph context at query time. Pipeline-run history follows a third operational path so status reporting never becomes entangled with knowledge retrieval.

Lifecycle view

A turn moves through accepted, prepared, executing, streaming and completed. Mutating tool calls can pause for approval, and missing information can pause for user input; both resume from checkpoints. Recoverable failures enter a bounded retry loop. Only exhausted retries or explicit cancellation produce terminal exits. Explicit state makes the system debuggable instead of leaving failure behavior to framework defaults.

One system five angles

The architecture has to survive contact with legacy constraints.

What exists, what happens first, who calls whom, where data moves, and what state the work is in must all describe the same system. When those five views agree, the design is more than a static diagram: it is an operating model that can coexist with a mature platform.
